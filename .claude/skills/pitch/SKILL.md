# Pitch and submission material

## Clarify first

Ask for: time limit of the pitch, judging criteria, audience (technical or
not), and the required submission format. Do not invent these.

## Source of truth

Describe only what exists. Read the code and run the app before claiming a
feature works. Mark anything planned but not built as "next steps". Never
invent metrics, user numbers or testimonials.

## Pitch outline (adapt to the time limit)

1. **Hook** — the problem in one sentence, with a concrete person who has it.
2. **Problem** — why it matters, why current options fall short.
3. **Solution** — what the product does, in plain words.
4. **Demo** — the live flow; this is the bulk of the time.
5. **How it works** — architecture in one diagram, the interesting technical bit.
6. **Impact / what's next** — who benefits, next steps, the ask.

Map each section to the judging criteria and say which criterion it serves.

## Deliverables

- `README.md` — description, screenshots, how to run, stack, team.
- `docs/pitch.md` — outline with speaker notes and timing per section.
- `docs/demo-script.md` — exact clicks and lines for the demo, plus the fallback.
- Short submission blurb (1 sentence, and a ~100-word version).

Keep the language concrete and short. One idea per slide.
